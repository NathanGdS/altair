Altair

A Kafka-inspired, append-only message broker built from four goroutines, two channels, and a folder full of JSON files. No cluster, no partitions, no offsets — just a filesystem doing the job of a commit log.

go 1.24 net/http go.uber.org/zap htmx + bulma dashboard module github.com/nathangds/altair

High level

The mental model

Altair accepts a message over HTTP, appends it to a plain file, and later moves it into another plain file on a schedule. If you can read JSON lines with tail -f, you can debug this system without a single client library.

The design deliberately borrows Kafka's vocabulary — publish, consumer, retention — while swapping every heavyweight piece for the simplest thing that could plausibly work: a buffered Go channel instead of a distributed log, a directory of JSON files instead of segments, and time.Sleep loops instead of a scheduler. There is exactly one broker process and zero coordination between nodes, because there are no other nodes.

Low level · real sequence

A message's lifecycle

This is the one place numbering means something in this document — it's the actual order of events for a single message, from socket to deletion.

01 · publish

POST /publish decodes and stamps the message

The handler decodes the JSON body into a Message, then calls Instantiate(), which assigns a UUID, sets ReceivedAt to time.Now().UTC(), and requires a non-empty origin — unless stress-test: true is set, in which case origin defaults to "stress-test". A missing origin without that flag is a 400.

handlers/publish_handler.go — PublishHandler, Message.Instantiate
02 · buffer

The message drops into a 200,000-slot channel

The marshaled message is pushed onto the package-level fileWriterChan (buffer size 200,000). This is what makes /publish return fast — the HTTP handler never touches disk itself.

handlers/publish_handler.go — fileWriterChan
03 · persist to ready

One goroutine serializes every write

A single fileWriterWorker, started from init(), drains the channel and appends the message as one JSON line to messages/ready/{origin}-{YYYY-MM-DD}.json, adding a leading newline if the file isn't empty. Being single-goroutine is what keeps concurrent appends to the same file safe without a lock.

handlers/publish_handler.go — fileWriterWorker, writeToFile
04 · consume

Every 5 seconds, ready/ gets scanned

ConsumerWorker lists every file in messages/ready, opens each one, and streams non-empty lines into a 5,000-slot msgChan. Once a file has been fully read it's truncated with os.Truncate — not deleted — so the same day's file keeps accepting new lines.

workers/consumer_worker.go — ConsumerWorker, readMessagesFromFile
05 · fan out

NumCPU × 2 goroutines drain the channel

A worker pool sized to runtime.NumCPU() * 2 consumes msgChan concurrently and calls saveProcessed for each line. This is the only step that runs with real parallelism.

workers/consumer_worker.go — processMessages, shared.ConsumerWorkingPool
06 · persist to processed

Lines land in an hourly bucket file

Each consumed line is appended verbatim to messages/processed/{YYYYMMDD_HH}.json — one file per hour, shared across all origins.

workers/consumer_worker.go — saveProcessed
07 · purge

Every 15 minutes, old lines are rewritten away

PurgeMessagesWorker reads every processed file, keeps only lines whose ReceivedAt is within the last 15 minutes, writes the survivors to a .tmp file, then removes the original and renames the temp file over it. There is no separate deletion step for expired messages — they simply aren't rewritten.

workers/purge_messages_worker.go — purgeMessages, removeLineFromFile
08 · retire the file itself

Empty files are quarantined, then wiped

Every 5 minutes, RemoveEmptyFilesWorker checks both messages/ready and messages/processed for zero-line files and moves them into messages/trash. Every 15 minutes, DeleteMakedFiles removes everything sitting there. The two-step handoff exists so a file being renamed away is never also the file a reader has open.

workers/remove_empty_files_worker.go — RemoveEmptyFilesWorker, DeleteMakedFiles
Low level

Package tour

Four packages, each with one job. Nothing imports in a cycle.

handlers/ — ingress

The only package that touches the network on the write path.

  • Message struct + validation
  • PublishHandler — the HTTP entry point
  • fileWriterChan / fileWriterWorker — the async write path

workers/ — background loops

Every goroutine that runs on a timer instead of a request lives here.

  • ConsumerWorker — ready → processed
  • PurgeMessagesWorker — retention
  • RemoveEmptyFilesWorker / DeleteMakedFiles — cleanup

web/ — operator dashboard

A small HTMX + Bulma UI, entirely read-only against the filesystem.

  • GET / — renders web/templates/home.html
  • GET /status-report — polled every 1s by the page itself
  • Counts lines under messages/ to compute a delivery percentage

shared/ — cross-cutting

The only package every other package is allowed to depend on.

  • shared.Log — the process-wide zap logger
  • Interval constants: purge, consumer, cleanup
  • ConsumerWorkingPool = runtime.NumCPU() * 2
Low level

Storage layout

The filesystem is the database. Three directories, each with a distinct role in a message's life.

messages/ ├── ready/ # inbox — written by handlers, read by ConsumerWorker │ └── {origin}-{YYYY-MM-DD}.json # one JSON object per line, truncated after each read ├── processed/ # delivered — written by ConsumerWorker, trimmed by PurgeMessagesWorker │ └── {YYYYMMDD_HH}.json # hourly bucket, all origins mixed together └── trash/ # staging area before permanent delete └── {original filename} # wiped by DeleteMakedFiles every 15 min

Low level

HTTP surface

Three routes. No auth, no middleware, no versioning.

POST  /publish

Accepts a message, returns it stamped with id and received_at.

GET  /status-report

HTMX partial, polled by the dashboard every second.

Request
curl -X POST localhost:8080/publish \
  -d '{"origin":"orders","data":{"order_id":42}}'
Response — 200
{
  "origin": "orders",
  "id": "c1a9e6c2-...",
  "data": { "order_id": 42 },
  "received_at": "2026-08-12T14:03:11Z",
  "stress-test": false
}

Missing origin without "stress-test": true → 400 with the error text as the body.

Operator view

The dashboard

web/templates/home.html loads Bulma and HTMX from a CDN and renders a single HTMX-driven partial that re-fetches /status-report every second — no JavaScript beyond what HTMX injects.

Low level

Observability

Every package logs through shared.Log, a single *zap.Logger configured with the production JSON encoder, ISO-8601 timestamps, capitalized levels, and an INFO floor, writing straight to stdout. There is no log or fmt logging anywhere in the codebase by convention.

Example line
{"L":"INFO","T":"2026-08-12T14:03:16.201Z","M":"Message appended to: messages/ready/orders-2026-08-12.json"}

main.go also wires graceful shutdown: SIGINT/SIGTERM trigger server.Shutdown with a 5-second context, and Log.Sync() is deferred at process start.

Known limitations

Grounded in what the code actually does today, not a roadmap.

  • ›Single process. No clustering, no replication, no leader election — one Altair instance is the entire system.
  • ›No consumer registration. processSingleMessage only writes to processed/; the code marks HTTP delivery to real subscribers as a future TODO.
  • ›No offsets or replay. Once a ready file is truncated, that data's only trace is whatever landed in processed/ — and that's purged after 15 minutes.
  • ›No auth. /publish accepts any request from anyone who can reach port 8080.
  • ›Purge rewrites whole files. PurgeMessagesWorker re-reads and re-writes every processed file each cycle — fine at current volume, a bottleneck at high message rates.
